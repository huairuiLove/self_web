# AI Agent 面试经验：把“我做过”讲成可验证的工程能力

> 这篇不是题库，而是一套把项目经历讲清楚的面试方法：先交代背景，再说明判断，最后用数据和复盘证明结果。

## 1. 自我介绍不要从名词开始

面试开场建议控制在 60 到 90 秒，按照「定位 → 问题 → 方案 → 结果 → 方向」组织：

> 我主要做 LLM 应用和 Agent 工程，最近负责一个需要多步检索、工具调用和结果校验的系统。最初的问题是模型经常调用错误工具、重复检索，线上延迟和成本都不稳定。我把流程拆成显式状态机，引入工具 schema 校验、超时重试和离线评估集，最终把成功率从 X 提升到 Y，平均延迟降低 Z%。接下来希望继续做 Agent 的可靠性、评估和平台化。

不要把“熟悉 LangChain、RAG、Multi-Agent”当成经历本身。面试官更关心你解决了什么约束，以及为什么这样设计。

## 2. 项目深挖的五层追问

准备每个项目时，至少回答下面五层：

1. **目标层**：用户要完成什么任务，成功如何定义？
2. **架构层**：为什么选工作流、单 Agent 或多 Agent？状态在哪里保存？
3. **执行层**：模型怎样选工具，工具失败后怎样重试或回滚？
4. **评估层**：离线集怎么构造，线上看成功率、成本、延迟还是人工接管率？
5. **治理层**：如何防 prompt injection、越权调用、敏感数据泄露和无限循环？

如果只能回答“模型生成 prompt，然后调用 API”，说明项目还停留在 demo 层。工业系统必须有执行器、边界和观测指标。

## 3. 系统设计题的白板顺序

遇到“设计一个客服 Agent / 研究 Agent / 自动化 Agent”，我会按这个顺序画：

```text
用户请求
  -> 意图识别与风险分级
  -> 任务状态 / 计划
  -> 模型决策
  -> 工具网关（schema、权限、超时、审计）
  -> 结果校验与记忆更新
  -> 回复 / 人工接管
```

先讲最小闭环，再补能力。不要一开始就堆多 Agent、向量数据库和复杂框架；如果一个有界工作流能解决问题，优先选择它，因为更容易测试、观测和控制成本。

## 4. 高频问题的回答骨架

### 为什么不用普通工作流

当步骤固定、输入输出明确时，普通工作流更稳定。Agent 适合存在不确定路径、需要动态选择工具或根据 observation 调整计划的任务。我的选择依据是路径熵、工具数量、失败代价和可解释性，而不是“Agent 更先进”。

### 如何降低幻觉

先缩小模型可自由发挥的范围：检索并保留来源、工具返回结构化结果、要求引用证据、对关键字段做规则校验。最后用拒答和人工升级兜底。只增加 prompt 通常不能解决事实性问题。

### 如何评估 Agent

至少拆成任务成功率、工具选择准确率、参数正确率、轨迹长度、延迟、token 成本和安全违规率。离线评估看固定数据集，线上评估看真实任务分布，并保留完整 trace 供失败归因。

### 多 Agent 什么时候值得用

只有当角色之间有清晰边界、可以并行或互相校验，并且协作收益超过通信成本时才使用。多 Agent 会带来更多 token、状态同步和故障点，不能替代清晰的任务分解。

## 5. 一次失败复盘应该怎么讲

用「现象 → 根因 → 修复 → 验证 → 后续」五句话：

- 现象：某类请求平均耗时突然升高，重复调用比例增加。
- 根因：工具错误没有进入状态，模型每轮都把任务当成新任务。
- 修复：为执行器加入显式状态、幂等键和重复调用上限。
- 验证：回放线上 trace，并在压力集上比较成功率、延迟和成本。
- 后续：补充状态迁移测试和超时告警，避免同类回归。

这比说“后来优化了 prompt，效果变好了”更能体现工程能力。

## 6. 面试前 24 小时 checklist

- 能用 90 秒讲完一个项目，并说出真实指标。
- 能画出 Agent 的状态、工具网关和失败路径。
- 能解释 RAG、ReAct、Plan-and-Solve 的适用边界。
- 准备一个失败案例，包含根因和验证过程。
- 记住至少一个安全风险和一个成本优化方案。
- 把论文结论翻译成自己的工程判断，而不是背摘要。

最后，面试经验的核心不是预测题目，而是让每个结论都能回到背景、约束、证据和 trade-off。
